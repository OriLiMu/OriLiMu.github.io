# 计算机本科生花大量时间写编译器，操作系统是不是不务正业？

两条功利主义的道路居然出现了二元对立，真是幽默。

他们学习计算机底层的理由真的是出于对技术的追求和热爱吗？

这类学生绝大部分都是看了诸如”学完了XXX就能超过90%的程序员“的类成功学言论，正好他们对自己的学习能力有一些自信，觉得自己可以逆着潮流把艰难的部分学完，然后弯道超车降维打击其他只学了Web开发的学生，期待着这个选择能带给自己竞争优势，这种思潮本身就是极其功利和带有强烈恶性竞争思维的，其功利性绝对不亚于代码刷题和面试八股文。

他们学习的方法又是什么？

理想情况是看着经典的黑皮书教材，顺着大佬的思想，用自己的代码把轮子再造一遍。

现实的情况是看着B站或者别的平台分享的教程，跟着老师把编译器的代码从视频里抄到自己的IDE上。

这个过程哪有什么理想主义和对知识的追求？

所谓的嗤之以鼻其实是输不起罢了，功利主义也不是什么时候都能打赢的，功利着功利着打输了被甩开了可太正常了。

事实就是大学生把时间花在底层学习上无法在就业市场上带来优势，他们学习底层架构的起点就是对就业市场的误判。

而知乎的众多老程序员们是在工作的几十年里反复接触到底层领域，深刻的体会到了这些内容对于工作的价值，但是他们又误判了自己的观点对学生会有什么影响，他们没想到“对技术有追求”的人设居然成了功利主义全新的目标，而实际上两派人考虑的压根不是同一回事。

真是滑稽。

回想一下以前试图劝说的几次案例，发现很多人其实是在装清高；

他们真正想要的是，即获得他人对技术大佬的尊重，又能在初期职场混的风生水起，这是一种更强烈的急功近利，只不过他们不幸走偏了方向没有获得成果，没能获得在别人面前上嘴脸的基础条件。

屠龙术没什么神秘可言注：强调一下，课内知识在这里被当成每个学生的出厂配置，这里批评的是"大学生学黑皮书"这种行为，而不是建议大学生忽略操作系统的必修课。

在跨过混吃等死的阶段和学完课内课程的艰难过程后，许多学生被网络上的某些教程和文章鼓励着走向死钻技术细节和底层原理的道路，把大量的时间花在接下来几年都无法帮助你的内容上，美其名曰为"打好底子"、"学习内功"，对世俗的事物不屑一顾，最后在初期的竞争中失去优势，被快速发展的其他同行狠狠甩开。

这种技术至上的观点，通常由几十年经验的老程序员发表出来，他们大学刚毕业的时候恐怕并没有执行相同的步骤，而是工作了几十年之后深刻意识到了某些技术和思想的重要性，马后炮式的后悔过去，却完全不考虑当年制约自己的现实因素。

计算机科学的知识体系是一层层嵌套的，由于重重抽象包装，底层知识和高层应用的学习出现了彻底的分离，哪怕你不知道指针是什么，也一样可以开发出一个功能充足的网站。

在这样的背景下，对高层应用的学习就显得功利和浅薄，而对底层知识的学习，就像基础学科之于工科一样，被奉为圭臬。

但如果真的去进行底层知识的学习，便会发现那里的学习方式同样浅薄和不堪一击。

没有足够的项目经验和现实考量，何从知道什么情况下会有更多的性能损失？

又怎么知道如何扩展开发会增加项目的耦合性？

对底层知识的学习同样是重新造轮子，还都是看着大佬写好的思路去造轮子，创造性也不见得比Web应用强上多少。

很多人把Web开发这种就业导向的学习当成实用主义和功利主义的糟粕，却把对底层知识的学习美化成一种对知识的追求。

事实上大部分学生对计算机底层的学习同样是一件功利的事，他们并不是真的为了真理或知识，他们只是听了类似于"学完了计算机底层原理就能超过90%程序员"的忽悠，以为选择一条更艰难的道路就能快速拉开和周围人的差距，结果被陡峭的学习曲线拦在半路。

荒诞的是，二元对立出现在了这两条同样功利的道路上，都是功利主义，又何来高低贵贱？

它们的唯一区别仅是应用开发在就业市场更有优势。

技术细节可以在了解软件工业之后再去深挖，而职业生涯最前期积累工作经验的机会错过了却很难再有第二次。

这不是实用主义和功利主义的胜利，这是理解了就业市场的功利者打赢了没理解市场的功利者。

另一方面，相比高层框架的应用，业余时间想要学底层方向，很难熬过那艰难的学习曲线。

每一本黑皮书都有两个游戏本的厚度，耐心读完再把学到的内容复现在代码上，次次都需要几个月的时间，获得的成就感又远不及开发Web项目，强烈的挫败感会迫使很多学生中途放弃。

那些工作多年的老程序员纷纷对黑皮书的精妙表达敬佩，是因为那些他们在数年的工作中反复接触到的黑盒领域，都被这些书精致的整理了起来，对于他们来说，这些内容的学习曲线远不如学生所经历的陡峭和令人挫败，他们能从这些内容的学习中获得足够的激励和满足，而没有经验的学生是做不到这点的。

事实上推动底层工具二次开发的大都是主攻高层应用开发的大型企业，底层工具和高层应用像衔尾蛇一样互相影响着对方，许多底层工具的设计选择，来源于高层应用的实际需求，那些成熟的设计规范和设计思想，在真正遇见问题之前是不可能被开发出来的。

同样的，在没有了解真实的项目开发流程之前就强迫自己学习迭代衍化出来的技术理念，其实是一种不切实际的拔苗助长。

重看当下：何为基础知识？

显而易见的是，这些吹捧编译器和操作系统的开发者们，他们选择的假想敌全都是以Web和移动端开发为主的应用开发者，网络上充斥着大量”认真学习底层原理的我吊打见识短浅的Web开发”的中二小故事，却很少见到这些所谓的学院派去碰瓷图形学、并行计算和深度学习，这可真是出乎意料，难道仅仅因为不学习编译器，Web开发者就会陷入劣势，而ML工程师就不会吗？

长期以来，"编译器""操作系统""性能计算"这样的字眼，莫名其妙的被和"应用开发""前端""CRUD"设在二元对立的两端，这是一套逻辑上完全说不通的话术，除了开发Chromium和Firefox的少数程序员，剩余的前端开发者一辈子也不会把JS优化到操作系统内核层面的，如果初学者非要代入那间办公室的十几个人才能开始学习，那就多少显得有些自我意识过剩了。

不同抽象层级的”底层“和”顶层“是一种相对的概念：对于前端开发师而言，编写JavaScript才是平时工作的主流，深钻的技术可能是代码DOM的运行原理和React框架的内部构造；

对于Java后端而言，性能的优化取决于开发者对JVM虚拟机的原理了解；

对于数据库工程师而言，底层原理则是查询和索引优化的不同策略。

很显然，在不同抽象层级定义“底层原理”的时候，所选择的目标是完全不一样的，不是每个人的职业道路都需要学习编译器的构造，也不是每个人都需要在Linux上从头搭建服务器。

对大部分开发者来说，编译器的知识可能仅仅能提供一个“我已经理解整个系统”的安全感和自信心（错觉），提供一点聊胜于无的情绪价值。

以2025年的视角来看，这套二元分类叙事也已经严重过时了，最近五年的流行求职方向全都无法嵌合进这套旧的框架（分布式、大数据、深度学习、图形学、HPC ...)，在这个写点SQL都算是原教旨学术派CS的时代，继续闷在”顶层“和”底层“的帽子底下可就不体面了。

不同技术路线下的基础技术早已变得大相径庭：机器学习的理论基础是统计，图形学的理论基础是线性代数，并行计算的理论基础是矩阵计算。

对于这些新兴的计算机分支来说，编译器和操作系统基本可以说是八竿子打不着的东西，如果需要学习更深入的技术原理，那也该去学它们各自领域对应的基础知识，而不是把学生阶段最宝贵的时间花在和初期工作八竿子打不着的屠龙术上。

中大型项目的编译流程既然针对后续 Git 章节的质疑如此之多，不妨先展示一下你们最钟爱的项目编译流程对于企业级的项目开发，尤其是C/C++这种编译性语言，搭建编译环境时开发流程中最重要且最复杂的一环，为了节约时间和降低出错率，企业通常会准备一个负责编译环境和编译工具的团队，持续性的更新各个团队使用的编译脚本，并尽可能精简编译操作的复杂性。

虽然内部编译工具将编译的复杂性抽象简化成了一个易用的工具，但是再简单的工具也不可能真正做到一键修改，开发者还是需要告诉编译器：“这是我修改的Repository，编译”。

对于几千个人同时参与开发的大项目，项目代码必然需要被拆分成多个module或者类似的概念结构，而开发者进行的修改，通常都是在这其中一两个module上增加新的commit；

而考虑到成本和编译时间，编译工具绝对不会将所有module都进行重新编译，实际上被重新编译的代码只有那几个小模块。

简单来说，对于个体开发者来说，项目编译流程大概是:（1）clone整个项目repo（2）设置repo本身的branch/commit（6）（3）找到修改的module（4）merge/cherry-pick修改的commit（5）到repo的母目录，或者编译脚本所在的目录，执行。

一个具有正规Code Review流程的企业，必然不会让开发者随意将新的修改合并至main branch，一个module内的小修小改还不算那么伤筋动骨，如果涉及到多module甚至多repository之间的通信，必然涉及至少两层的Code Review，这个新的commit需要先进行测试才能考虑合并，在merge之前进行build是必须的。

而对于大型项目，传统Git服务和Code Review流程对于管理复数个团队同时进行修改显得力不从心，Gitlab和Gerrit这种集成CICD Pipeline的现代化Git工具被逐渐应用，在一个commit被推送至Code Review之前，需要通过多层自动化CICD编译测试，单元测试和集成测试。

让我们假设这么一个常见的场景，一个项目有repository A（服务器），repository B（客户端）和repository C（硬件本身）的软件开发组成，现在我们需要在repository A增加一条消息，修改需要在repository A里的三个module同时进行，并且由不同的开发者完成，每个module都有好几条独立的commit，整个开发必须要在repository A的特定历史版本上进行，现在需要构建一个build，然后拿去和repository B和repository C的最新build进行组合测试，大家可以自己观察整个流程中参与最多的工具是什么。

综上所述，大伙心心念念的“编译器”在绝大部分的真实项目开发里基本只是一个脚本，而整个编译流程里最麻烦的一项工作变成了，怎么让这些全新的修改被放置在不同revision里的不同module里并且没有在编译脚本执行时报错；

开发者在编译流程里遇到最多困难的，不是已经被封装的基本看不见的编译器，而是那个负责版本管理的Git，用于扩展Git的Gitlab和Gerrit，以及他们后面那乱七八糟的黑箱CICD Pipeline。

真正的基本功：Git 重要性与难度无关人们常说学习底层原理是在练习"基本功”，这个说法毫无逻辑可言，你不能因为一种技术是另一种技术的底层构成就称其为"基本功"。

我们可以说"循环"是一切编程语言入门的"基本功"，没有它将会寸步难行；

也可以说"原子锁"是多线程编程的"基本功"，它对实现Mutual Exclusion至关重要；

但说编译原理是后端开发的"基本功"就完全没有道理，即使对于很多C++和广义上的底层开发岗位而言，编译器的原理和开发工作的相关性也依旧不高。

匪夷所思的是，这些重度技术洁癖鼓励新手将90%的时间花在语义分析器这种在工作中占比不到10%的内容上，却彻底忽视Git这类真正在工作中90%的时间都在使用的实用工具。

Git的相关教程通常十分简洁: git checkout, git add, git commit, git push, git merge，绝大部分大学的课程对Git的探索就止步于此了，稍微有一点进取精神的会多教两句git rebase, git cherry-pick，但绝大多数程序员根本不知道HEAD指针的存在，分不清origin/master和master的区别，也理不顺git reset和git restore的使用场景，而这些问题将会在进入职场后大量的暴露出来，引来一系列污染个人开发流程的麻烦。

在中大型企业中的巨型项目开发，几千个开发者同时向一个巨型项目频繁的提交代码，由于代码量过于庞大且难以组织，公司会选择使用git submodule和git subtree将项目模块化；

而为了自动化项目构建和代码提交，大量的CI/CD工具被应用到项目中，整个项目对于单个开发者而言会变得空前复杂。

为了提高效率，每个团队会各自使用符合各自风格和需求的提交流程，有的会在rebase和merge之间做出选择，有的会准备封装了Git操作的脚本，有的会用Git Hooks自动化代码提交流程。

而刚进入团队的新人，会遵循一套团队制定的代码提交流程，并且在这个过程中，他很可能执行一些他不知道意义的操作。

git merge 和 git rebase 的区别总是被人反复学习和反复遗忘，许多学习者只是尝试简单地记住不同的使用场景，并未思考这些操作对代码commit history的影响。

在执行merge和rebase操作时，很少有人会考虑到指针的具体变动。

在这种条件下，对Git的底层原理有深入理解变得尤为重要，否则新加入团队的开发者可能会频繁遇到因不清楚原因而导致的推送被拒绝，提交信息被系统拦截，甚至丢失（无法找到）他们刚编写的代码。

遗憾的是，大学和企业的运营模式存在显著差异。

在大学的研究实验室中，参与同一项目的开发人员通常不会超过十人。

在这种规模下，简单的Git和GitHub的使用已经足够应对所有项目管理需求，引入如GitLab和Gerrit这样的复杂管理工具显得过犹不及。

于是负责教课的大学教授往往忽视了Git在版本管理中的关键作用及其背后的运行原理，让Git坍缩为一个与GitHub配合使用的代码存储工具。

在所有新开发者能接触到的工具中，Git是最应该系统化理解的，解决不了系统优化问题还没那么丢人，误操作Git拖慢开发进度才是真正的棘手。

想要几乎一劳永逸的解决此类麻烦（几乎），理解每个Git操作背后的指针逻辑是必须的，记住每个Git命令的所有选项不现实，但花费几个小时来系统性地了解Git及其每个命令的基本功能是完全可行的。

你不需要知道或记住每一个命令后缀的意义，但只要得知道哪些需求可以向GPT索求一段命令。

笔者在这里给学弟学妹们强烈推荐Pro Git这本书。

这是一本随着同步Git版本更新的免费工具书，阅读所需时间远少于学习任何一个技术栈（跳过过时和对入门开发没有助益的章节，阅读时间<10h）。

在阅读过程中，不必跟随操作，只需理解每个命令背后的原理及其能力的界限即可。
